# Prompting Claude Sonnet 5 and Claude Opus 5.5

## Summary

Anthropic's current guides answer three questions the harness had left to
taste. A prompt's formatting carries into the reply it produces, so a prompt
that asks for prose is written in XML tags and not under Markdown headings. A
skill's description is written in the third person and leads with the words a
request contains, and where a skill has to be in context before the model acts,
the platform's own advice is a hook, because a model choosing to load it is not
deterministic. A prompt hook blocks by answering `{ok: false, reason}`, which is
not the field ADR-1010 names.

I measured the routing question as well: in a clean repository on Sonnet 5, the
`meow-prose` skill loaded in one run of nine across three writing requests.

Research for how the harness writes the prompts it ships: skills, agent
definitions, the output style, the subordinate-agent fragment and hook prompts.
It does not cover what a skill costs, which is
[RES-0005-skill-format.md](RES-0005-skill-format.md), the authoring surface
in general, which is [RES-0201-skill-authoring.md](RES-0201-skill-authoring.md),
nor how a prompt is measured, which is
[RES-0266-measuring-the-harness.md](RES-0266-measuring-the-harness.md).

## The question

The harness ships prompts designed for Claude Sonnet 5 and Claude Opus 5.5.
Three things about them were argued and never sourced: which structure a
prompt uses, how a skill that must hold gets loaded, and how a prompt hook
says no. The first draft of the `meow-prose` skill used Markdown headings, was
rarely loaded, and was paired with a gate whose blocking field came from the
wrong kind of hook.

## Method

I read these pages at their source on 2026-09-22: Anthropic's prompting best
practices, its pages for Sonnet 5 and Opus 5.5, its skill authoring best
practices, and the Claude Code pages on skills and hooks. Each finding below
names the page it comes from.

I measured routing in a scratch repository holding one staged file, with
`meow-prose` installed at local scope and no other writing skill present. Each
request ran in a fresh `claude -p` session on `claude-sonnet-5`, and a run
counted as a hit when the transcript showed a `Skill` call naming the writing
skill. Three requests ran three times each.

## Findings

### A prompt's formatting carries into its reply

The best-practices page says the formatting style of a prompt influences the
style of the response, and that removing Markdown from a prompt reduces the
Markdown in the output. It recommends telling the model what to do rather than
what not to do: "smoothly flowing prose paragraphs" in place of "do not use
markdown".

The same page recommends XML tags where a prompt mixes instructions, context,
examples and variable input, with consistent, descriptive tag names, nested
where content has a hierarchy. Examples go in `<example>` tags so the model
tells them apart from instructions.

For the harness this means a prompt that teaches prose is written in tags, and
a Markdown skeleton works against the prose it asks for.

### Sonnet 5 follows instructions literally and learns from positive examples

The Sonnet 5 page says the model interprets a prompt literally, does not
generalise an instruction from one item to another, and does not infer a
request nobody made, so a prompt states the scope it means. It also says a
positive example of the wanted form works better than a negative example or an
instruction saying what not to do.

For code review it warns that "only report high-severity issues" lowers
measured recall on Sonnet 5, because the model follows the bar it was given.
The page recommends that a finding stage report every issue with a confidence
and a severity, and leave filtering to a later step.

### Opus 5.5 resists injected text when outside text is marked

The Opus 5.5 page says the model resists instructions inside pasted content
when the application marks which text is the user's and which came from
elsewhere. The mark is an opening and a closing tag carrying the same short
random identifier generated by the application, each on its own line, with a
note in the system prompt that instructions inside the tags are followed only
where the user's own message asks. The page adds that tags are plain text and
can be imitated, so the mark is one guard among several.

### A description is written in the third person and leads with the request's words

The skill authoring page says the description is injected into the system
prompt and must be written in the third person, because an inconsistent point
of view causes discovery problems. It says the description states what the
skill does and when to use it, with the terms a request would contain. Names
are lowercase with hyphens, and the gerund form (`processing-pdfs`) is the
recommended pattern.

The Claude Code skills page adds a `when_to_use` field whose text is appended
to the description, and says the combined text is cut at 1,536 characters in
the listing, so the key use comes first.

### A skill the model must load is not left to the model

In my measurement the writing skill loaded in no run of three for "write the
commit message for the staged change", none of three for a short install
section, and one of three for a pull request description. The session listed
the skill every time. Rewording the description as a directive changed
nothing on the commit request.

The Claude Code skills page says that where a skill stops influencing
behaviour, the fix is a stronger description or a hook that enforces the
behaviour deterministically. The best-practices page warns that aggressive
wording such as "CRITICAL: you MUST" makes recent models over-trigger, and
recommends ordinary phrasing.

The hooks page says a `SessionStart` hook runs on every new, resumed, cleared
or compacted session, accepts only a command hook, and can return
`additionalContext`, which the platform inserts as a system reminder before
the first prompt. A hook's added context is capped at 10,000 characters.

### A prompt hook says no with `ok` and `reason`

The hooks page says a `prompt` hook sends its prompt and the hook's input to a
fast model, Haiku by default, which answers `{"ok": true | false, "reason":
"..."}`. On `PreToolUse`, `ok: false` denies the call and by default ends the
turn with the reason shown as a warning; `continueOnBlock: true` returns the
reason to the model as the tool error instead, so it can correct the call and
continue. `permissionDecision: "deny"` is the field a command hook returns.
The default timeout is 30 seconds, and `$ARGUMENTS` places the hook input in
the prompt.

### Concise prompts, measured on the models they serve

The skill authoring page says to assume the model is already capable, to add
only what it lacks, and to ask of each paragraph whether it justifies its token
cost. It recommends building evaluations before writing extensive instructions,
writing the minimum that passes them, and testing a skill on every model it is
meant for.

The Opus 5.5 page says to remove chat instructions that ask the model to think
carefully, because effort is the control for thinking and the line only
delays the reply.

## Conclusions

1. A prompt the harness ships marks its parts with XML tags throughout and uses
   no Markdown headings as its skeleton, because a prompt's formatting carries
   into the reply and the harness asks for prose.
2. A prompt states what to do and shows the wanted form in a positive example,
   and a failing example sits beside it rather than alone.
3. A prompt states the scope it means, because Sonnet 5 does not generalise an
   instruction beyond the item it names.
4. Text from outside the harness inside a prompt is marked as outside text, and
   where the harness assembles the prompt the marking tags carry an identifier
   generated for that call.
5. A description is written in the third person, says what the unit does and
   when to use it, and leads with the words a request contains.
6. A unit that has to be in context before the model acts is loaded by a
   `SessionStart` command hook returning `additionalContext`, because the
   model's own choice loaded the writing skill once in nine runs, and louder
   wording makes recent models over-trigger.
7. A prompt hook blocks with `ok: false` and a reason, and a gate that should
   let the model correct itself sets `continueOnBlock: true`.
8. A finding stage reports every finding with its confidence and severity, and
   filtering is a separate step, because Sonnet 5 honours a stated bar and
   drops what falls below it.
9. An instruction stays in a shipped prompt only while a measurement shows it
   changes the result on the models the prompt serves, Sonnet 5 and Opus 5.5.
